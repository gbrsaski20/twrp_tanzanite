  FLASH INSTRUCTIONS — TWRP for Redmi Note 14 4G (tanzanite)
  Recovery partition: vendor_boot
==============================================================================

DEVICE INFO
----------
  Device:        Xiaomi Redmi Note 14 4G
  Codename:      tanzanite
  Chipset:       MediaTek Helio G99 Ultra (MT6789)
  Android:       14 (HyperOS)
  Recovery type: vendor_boot image (V4 header)
  Bootloader:    Must be unlocked (Mi Unlock)

==============================================================================
  STEP 1: PREPARE YOUR DEVICE
==============================================================================

1. Unlock the bootloader (if not already done):
   - Download Mi Unlock Tool from https://www.miui.com/unlock/
   - Bind your Mi Account in Developer Options
   - Wait 168 hours (7 days) for the unlock timer
   - Boot to fastboot: power off -> hold Vol Down + Power
   - Run Mi Unlock and unlock

2. Enable USB Debugging:
   - Settings -> About phone -> tap "MIUI version" 7 times
   - Settings -> Additional settings -> Developer options
   - Enable "USB debugging"

3. Install minimal ADB & Fastboot on your PC:
   - Already have it at: F:\Tool RedmiNote14\Minimal ADB Fastboot v1.4.3.exe
   - Or download from: https://developer.android.com/studio/releases/platform-tools

==============================================================================
  STEP 2: BOOT TO FASTBOOT MODE
==============================================================================

Option A (from running system):
   adb reboot bootloader

Option B (from powered off state):
   - Power off the phone completely
   - Hold Volume Down + Power button together
   - Release when you see the fastboot bunny/rabbit logo

Verify connection:
   fastboot devices
   # Should show something like: 12345678  fastboot

==============================================================================
  STEP 3: FLASH TWRP RECOVERY TO vendor_boot
==============================================================================

*** IMPORTANT ***
The Redmi Note 14 4G stores recovery inside the vendor_boot partition.
Do NOT flash to "boot" or "recovery" partition — only to vendor_boot!

After building via GitHub Actions, download the image:
   1. Open: https://github.com/gbrsaski20/twrp_tanzanite/actions
   2. Click the latest successful run (green check)
   3. Scroll down to "Artifacts"
   4. Download "vendor_boot_twrp_tanzanite.zip"
   5. Extract -> vendor_boot_twrp_tanzanite.img  (~64 MB)

Or download from the Releases page (created on manual runs):
   https://github.com/gbrsaski20/twrp_tanzanite/releases

Copy the .img to F:\Tool RedmiNote14\ for convenience.

Optional sanity check (PowerShell) - header must say VNDRBOOT:
   $b = [System.IO.File]::ReadAllBytes("F:\Tool RedmiNote14\vendor_boot_twrp_tanzanite.img")[0..15]
   [System.Text.Encoding]::ASCII.GetString($b)

Flash command:
   fastboot flash vendor_boot vendor_boot_twrp_tanzanite.img

Example (if the image is in F:\Tool RedmiNote14\):
   fastboot flash vendor_boot "F:\Tool RedmiNote14\vendor_boot_twrp_tanzanite.img"

==============================================================================
  STEP 4: BOOT TO TWRP RECOVERY
==============================================================================

After flashing, boot directly to recovery (do NOT boot to system first!):

   fastboot reboot recovery

Or manually:
   - Hold Volume Up + Power button
   - Release when you see the TWRP logo

*** CRITICAL ***
On first boot to TWRP, if it asks to "Keep system read only" or
"Allow modifications", choose ALLOW MODIFICATIONS if you want to be
able to modify system partitions.

If TWRP doesn't stick after reboot (system overwrites it):
   1. Flash TWRP again:  fastboot flash vendor_boot vendor_boot.img
   2. Immediately:       fastboot reboot recovery
   3. In TWRP: Install any custom ROM zip, or flash Magisk to patch the ROM
   4. After that, TWRP should persist

==============================================================================
  STEP 5: BACKUP YOUR STOCK PARTITIONS (RECOMMENDED)
==============================================================================

Once in TWRP:
   1. Go to Backup
   2. Select: System, Vendor, Boot, Data, Vendor_Boot
   3. Backup to internal storage or SD card or USB OTG
   4. Copy backup to PC for safekeeping

==============================================================================
  STEP 6: VERIFY THE BATTERY FIX (A14_Tanzanite_battfix)
==============================================================================

The first build showed a constant 100% in recovery. The cause was inside TWRP,
not in the battery itself.

recovery_utils/battery_utils.cpp (TWRP android-12.1) contains:

    // If we can't read battery percentage, it may be a device without battery.
    // In this situation, use 100 as a fake battery percentage.
    if (res != Result::SUCCESS) {
        capacity = 100;
    }

On this device the HIDL health HAL does not answer inside recovery, so
res != Result::SUCCESS and TWRP pins the status bar at 100% permanently.

The fix sets in BoardConfig.mk:

    TW_USE_LEGACY_BATTERY_SERVICES := true

which makes twrp.cpp read /sys/class/power_supply/battery/capacity directly
and skip the health HAL entirely.

--- How to confirm you are running the fixed build ----------------------------

1) Main TWRP screen: the version string must read

       3.7.1_12-A14_Tanzanite_battfix2

   (variables.h concatenates TW_MAIN_VERSION_STR with TW_DEVICE_VERSION, so
   the marker is the "-A14_Tanzanite_battfix2" suffix.)

   Still showing A14_Tanzanite or A12+_AOSP  -> OLD image, reflash.
   Showing -A14_Tanzanite_battfix (no "2")   -> first attempt, does NOT work.

2) In TWRP -> Advanced -> Terminal, or via adb shell:

   cat /tmp/batt/capacity      <- what TWRP is displaying
   cat /tmp/batt/status        <- Charging / Discharging
   tail -5 /tmp/battfix.log    <- the raw maths, one line per 5 s

   A healthy log line looks like:
     12 v=4150000 i=-500000 voc=4197 vs=4197 soc=87 disp=87 st=Discharging

   Reading it:
     v     terminal voltage, microvolts
     i     current, microamps (negative = discharging)
     voc   voltage after internal-resistance compensation, millivolts
     soc   result of the OCV lookup
     disp  what got written to /tmp/batt/capacity

3) Compare with the node TWRP used to read:

   cat /sys/class/power_supply/battery/capacity

   This one will probably still say 100 - that is the point. The kernel gauge
   is wrong; we no longer use it. What matters is /tmp/batt/capacity.

--- Why the first attempt did not work ----------------------------------------

Attempt 1 only added TW_USE_LEGACY_BATTERY_SERVICES, so TWRP read
/sys/class/power_supply/battery/capacity directly. That fixed the health-HAL
fallback, but the node itself is stuck at 100 because the vendor fuel
algorithm has a wrong OCV table and an inverted current_now sign.

Attempt 2 (this build) stops trusting that node. battfixd.sh runs as a recovery
service, computes SOC in userspace from the honest bms voltage/current
(OCV = V - I*R, R = 95 mOhm fitted on tanzanite hardware), and writes the result
to /tmp/batt/capacity. TWRP is pointed there via TW_CUSTOM_BATTERY_PATH.

If /tmp/batt/capacity is missing or TWRP shows -1%, the daemon did not start:

   ps -A | grep battfix
   sh /system/bin/battfixd.sh     <- run it by hand to see the error

--- About "Android also jumps to 100% after visiting recovery" ----------------

TWRP only READS the gauge, it never writes it, so it cannot change what
Android reports. If Android shows 100% for a while after leaving recovery,
that is the fuel gauge re-learning its state on the next boot; it settles by
itself. It is not caused by the percentage TWRP displayed.

--- Reset baterai: apa yang bisa dan tidak bisa dilakukan di TWRP -----------

TWRP TIDAK punya tombol "reset fuel gauge". Yang ada cuma dua hal:

1) Hapus statistik baterai Android (aman, efek terbatas)
   Ini cuma menghapus catatan pemakaian Android, BUKAN kalibrasi gauge.
   Persentase tetap datang dari kernel, jadi angkanya tidak berubah.

   Di TWRP -> Advanced -> Terminal:
       rm -f /data/system/batterystats.bin

   Syarat: /data harus sudah terdekripsi (TWRP tidak minta password).
   Kalau muncul "Read-only file system", berarti /data belum ke-mount.
   File ini dibuat ulang otomatis oleh Android saat boot berikutnya.

2) Kalibrasi gauge yang sebenarnya (tidak lewat TWRP)
   Ini yang benar-benar memperbaiki pembacaan yang melenceng:
       a. Charge sampai 100%, lalu tetap tercolok 1-2 jam lagi
          (supaya gauge melihat "plato" tegangan penuh)
       b. Pakai normal sampai HP mati sendiri
       c. Charge tanpa putus sampai 100% dalam keadaan mati
       d. Nyalakan, selesai. Gauge belajar ulang.

   Di Android bisa juga lewat MTK EngineerMode:
       *#*#3646633#*#*  ->  Hardware Testing -> Power -> Fuel Gauge
   (di HyperOS kadang diblokir; kalau begitu pakai cara a-d di atas)

*** JANGAN HAPUS /mnt/vendor/persist ***
Di situ MTK menyimpan kalibrasi baterai (tabel OCV, battery ID, cycle count).
Kalau dihapus, gauge bisa jadi permanen salah dan harus recalibrate pabrik.
Tidak ada hubungannya dengan bug 100% yang kita perbaiki - itu murni bug
tampilan TWRP, gauge-nya sendiri tidak pernah rusak.

==============================================================================
  TROUBLESHOOTING
==============================================================================

Problem: "fastboot: error: device not found"
  -> Install USB drivers ( MediaTek Preloader USB VCOM Drivers in your tools)
  -> Try different USB cable (preferably original)
  -> Try different USB port (USB 2.0 preferred over hub)

Problem: TWRP boots but touch doesn't work
  -> The recovery tree includes touchscreen kernel modules
     (modules.load.recovery in the kernel tree). If touch fails, the
     modules might not have loaded. Check dmesg in TWRP.

Problem: TWRP boots but decryption fails
  -> The tree uses FBE (File-Based Encryption) with aes-256-xts.
     If you changed your PIN/password recently, reboot to system and back.

Problem: Build fails with missing dependencies
  -> Run: export ALLOW_MISSING_DEPENDENCIES=true
  -> Retry: mka vendorbootimage

Problem: battery still stuck at 100% after the battfix2 build
  -> Confirm the version string shows -A14_Tanzanite_battfix2 first.
  -> Check whether the daemon is alive and what it computed:
         ps -A | grep battfix
         cat /tmp/batt/capacity
         tail -20 /tmp/battfix.log
  -> No log at all / file missing -> service did not start. Run it by hand:
         sh /system/bin/battfixd.sh
     and read the error. Typical causes: bms node missing (it falls back to
     battery automatically) or voltage_now unreadable (permissions).
  -> Log exists but soc is always 100 -> the OCV table is too optimistic for
     your cell. Edit /system/etc/battfix_ocv.txt (copy it to /tmp first, the
     daemon re-reads /tmp/battfix_ocv.txt) or lower RMO.
  -> soc looks right but the screen still shows 100 -> TWRP is not picking up
     the path. Verify TW_CUSTOM_BATTERY_PATH made it into the build:
         strings /system/bin/twrp | grep tmp/batt

Problem: Out of memory during build
  -> Reduce jobs: mka vendorbootimage -j4
  -> Add swap: sudo fallocate -l 16G /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
